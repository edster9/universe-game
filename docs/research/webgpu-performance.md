# Browser 3D on WebGPU: performance, and the stack around it

Surveyed 2026-09-30 for choosing how the browser client is built: **(A)** a Rust client compiled to WebAssembly, drawing through WebGPU (wgpu, Bevy), possibly sharing code with the engine; or **(B)** a TypeScript client with a JavaScript WebGPU renderer (three.js, Babylon.js, PlayCanvas), with the Rust engine as a WebAssembly module where useful. It also covers physics, sound, and fast networking, since those shape the same choice. Sources are browser vendors' docs and blogs, engine docs, issue trackers, papers, and developer posts; forum posts, search excerpts, and aggregator sites are marked. This field moves fast, so every source carries its date. Nothing was tested first-hand.

## Summary

WebGPU now ships by default in Chrome and Edge (Windows, macOS, ChromeOS, most Android), Safari 26 (macOS, iOS, iPadOS, visionOS), and Firefox (Windows, Apple Silicon Macs). Linux and Firefox on Android are still partial. WebGPU's gain over WebGL is on the **CPU side**: cheaper draw calls and state changes, reusable command lists (render bundles), and compute shaders. Measured gains exist, but the big JavaScript engines' new WebGPU renderers are, in mid-2026, sometimes **slower** than their mature WebGL renderers on scenes with many separate objects; the costs are in the engines' bookkeeping, not the API. A Rust or C++ program compiled to WebAssembly reaches WebGPU only through the same JavaScript API, so each call crosses from wasm to JavaScript; no one has published a clean measurement of that cost, and the practitioners (Figma, Babylon, Toji) all say the cure is the same in any language: **fewer calls per frame** (batching, bundles, instancing, indirect draws). Where the GPU is the bottleneck (shading, resolution, post-processing), the client's language makes no difference. Where WebAssembly clearly wins is heavy CPU work such as physics and simulation, and it loses when code chats across the wasm–JavaScript boundary thousands of times per frame. Rust on the web still runs **single-threaded** in practice (Bevy, Godot's default export), since threads need special headers.

The later sections, in brief:

- **Physics (section 7).** Rapier and Jolt are the actively developed engines in wasm; Havok is fast but closed; ammo.js and cannon-es have stalled. Float engines can now give identical results on every machine, but only under strict conditions and at 0–8% cost; fixed point (Q48.16) is bit-exact at about twice the cost. Games compute orbits with their own code (KSP's patched conics) and use a rigid-body engine only in a small bubble. Rocket League runs Bullet at 120 Hz under full server authority, with clients predicting and being corrected.
- **Sound (section 8).** Everything goes through Web Audio, which mixes on its own thread, so the language matters only when a game mixes sound itself, and then the problem is threading, not speed. HRTF spatial sound is expensive; equal-power panning is cheap.
- **Networking (section 9).** WebSocket suffers head-of-line blocking; WebTransport (QUIC, with unreliable datagrams) has been in every major browser since Safari 26.4 (March 2026). The standard pattern is server authority with client prediction, interpolation, and lag compensation, and bandwidth is cut by quantising and sending only changes. lightyear is the most complete Rust library; AWS's Network Load Balancer passes QUIC through.
- **For us**, see "What this means for us" at the end.

## 1. Where frame time goes, and what WebGPU changes

**The command path.** Brandon Jones (Chrome's WebGPU team) describes what each command costs in a browser: the call is made in the JavaScript VM, marshalled "over to the GPU Process via our WebGPU wire protocol", decoded, "validated according to the WebGPU spec", translated to the native API (Vulkan, Metal, D3D12), then recorded by the driver. Render bundles skip much of this because "much of the validation and encoding was already performed at bundle encoding time". So in a browser, the cost per draw is higher than native, and the number of calls is what matters. (Updated 2024-01-22.)
Source: https://toji.dev/webgpu-best-practices/render-bundles

**Why WebGPU is cheaper per call.** Pipelines package all rendering state up front, and bind groups are validated when created, so "validation during execution and state switching are both cheaper than in WebGL" (ICS, 2023). Their demo on an M1 MacBook Air (Chrome 113) held about 50 FPS at 10,000 draw calls where WebGL fell to about 30. Kitware measured VTK's WebGPU backend drawing 1,000 separate objects in about 1.8 ms per frame by recording them into render bundles, where its OpenGL path stalled (2023-09-19; the post covers native and wasm builds, and which one gave that number is unclear). Figma, after moving its renderer to WebGPU, reported "a performance improvement when using WebGPU on some classes of devices, and more neutral results on others, but no regressions" (2025-09-18).
Sources: https://ics.media/en/entry/230426/ · https://www.kitware.com/faster-rendering-of-large-number-of-actors-in-vtk-with-webgpu/ · https://www.figma.com/blog/figma-rendering-powered-by-webgpu/

**Where the new renderers are slower.** WebGPU needs more calls per object than WebGL with vertex array objects: Babylon's team counted "between 6 and 10" per mesh, and explained a slow test scene as "API calls to the browser and those are taking time" plus JavaScript overhead for 22,500 objects (forum, 2021). three.js users measured WebGPURenderer at a quarter of WebGLRenderer's frame rate with 20,000 separate cubes; a maintainer blamed per-object uniform buffers causing "many `setBindGroup()`" calls (forum, 2025-02). The GitHub issue ("Current UBO system has severe performance issues") is still open and marked high priority. In May 2026 (three.js r183, RTX 4090) another user measured 4,000 meshes at 4.5 ms of CPU per frame in WebGLRenderer against 9.7 ms in WebGPURenderer, and a first frame 5 to 10 times slower; the same gap appeared on WebGPURenderer's WebGL fallback, so it's "a renderer-class cost, not a backend one" (forum). Unity's WebGPU backend showed the same pattern in 2025: a frame nearly twice as long as WebGL, with a third of CPU time in bind-group and uniform-buffer management; a Unity engineer called uniform uploads an area "on my list". The three.js manual itself says WebGPURenderer is "still in an experimental state" and that some scenes see "better performance with WebGLRenderer" (search excerpt, undated).
Sources: https://forum.babylonjs.com/t/why-webgpu-backend-is-slower/24091 · https://discourse.threejs.org/t/why-webgpurenderer-performance-significantly-lower-than-webglrenderer/77629 · https://github.com/mrdoob/three.js/issues/30560 · https://discourse.threejs.org/t/webgpurenderer-2x-slower-cpu-and-5-10x-slower-first-frame-than-webglrenderer-on-many-mesh-scenes-r183-same-on-both-backends/91904 · https://discussions.unity.com/t/unexpected-high-frame-cost-in-unity-6-webgpu-vs-webgl-questions-on-bindgroup/1653892 · https://threejs.org/manual/en/webgpurenderer.html

**What engines do about it.** Babylon's "snapshot rendering" records whole scenes into render bundles (WebGPU only). PlayCanvas added indirect draws on WebGPU (v2.11) "to shift more responsibility to the GPU and reduce CPU overhead" (search excerpt). Unity 6.6 lists, for WebGPU only, GPU Resident Drawer, GPU occlusion culling, and GPU particles (aggregator, below). The pattern: WebGPU pays off when the renderer is built around it (bundles, compute, GPU-driven culling), not when a WebGL-shaped renderer is ported.
Sources: https://forum.babylonjs.com/t/why-webgpu-backend-is-slower/24091 · https://radiancefields.com/playcanvas-v2-11-0-engine-released

**GPU-bound versus CPU-bound.** No source above measured a game's split between CPU and GPU in general. What they agree on: draw submission, state changes, and per-object bookkeeping are CPU costs, and in a browser they are larger than native, so a city with thousands of separate objects is at risk of being CPU-bound; shading, lighting, and resolution are GPU costs, the same whoever calls the API.

## 2. WebAssembly calling WebGPU

**Every call goes through JavaScript.** A wasm program has no direct route to the GPU. wgpu's web backend calls the browser's WebGPU through `web-sys` bindings (Chrome ecosystem page, 2025-09-16; wgpu docs), and Emscripten's `emdawnwebgpu` is "Dawn's implementation of webgpu.h for Emscripten (on top of the WebGPU JS API)". Figma, whose C++ renderer is compiled to wasm, wrote "some of our own custom C++/JS bindings in cases where these built-in bindings weren't performant enough", and batched uniform uploads for many draws into one to avoid regressions (2025-09-18).
Sources: https://developer.chrome.com/docs/web-platform/webgpu/webgpu-ecosystem · https://wgpu.rs/doc/src/wgpu/documentation/platforms/web.rs.html · https://dawn.googlesource.com/dawn/+show/HEAD/src/emdawnwebgpu/pkg/README.md · https://www.figma.com/blog/figma-rendering-powered-by-webgpu/

**How big the crossing cost is.** Mozilla measured in 2018 that plain wasm-to-JS calls became "almost as fast as JS to JS calls" (about 450 ms per 100 million calls), but calls into Web APIs still "have to go through JavaScript" glue because wasm then had only numbers as values. Reference types (`externref`) let wasm hold JavaScript objects directly and cut that glue; wasm-bindgen uses them when enabled. WebGPU's API passes objects and dictionaries, which makes its binding heavier than WebGL's integer handles (2017–2018 discussions between the WebGPU and wasm groups). **No published benchmark was found** comparing the same WebGPU workload driven from JavaScript and from wasm. Bevy's own examples page still calls its WebGPU web build "currently experimental" and defaults to WebGL2 (README, fetched 2026-09-30). A wgpu issue (2024-10) showed wgpu's own state-change tracking costing a lot next to raw Vulkan on native; it was closed as not planned.
Sources: https://hacks.mozilla.org/2018/10/calls-between-javascript-and-webassembly-are-finally-fast-🎉/ · https://docs.rs/externref/ · https://lists.w3.org/Archives/Public/public-gpu/2017Nov/0001.html · https://github.com/bevyengine/bevy/blob/main/examples/README.md · https://github.com/gfx-rs/wgpu/issues/6357

**Where wasm wins, and where it doesn't.** A 2019 study found C programs compiled to wasm ran on average 45% (Firefox) to 55% (Chrome) slower than native, with peaks of 2–2.5×; wasm is fast, but not native (USENIX ATC 2019). Physics is the clearest win: the Rapier (Rust, wasm) versus Matter.js (JavaScript) comparison is in section 7. The loss case is chatty code: a 2026 blog reported a Rust wasm JSON parser 25% *slower* than TypeScript, because each value crossed the boundary (secondary source). Earlier, Figma's switch to wasm cut load time "by more than 3x", mostly from faster parsing and cached compiled code (2017). Wasm also has no garbage collector in the Rust case, so no collector pauses; no measurement of JavaScript GC pauses in games was looked for here.
Sources: https://www.usenix.org/conference/atc19/presentation/jangda · https://www.kunalganglani.com/blog/rust-wasm-vs-typescript-performance · https://madebyevan.com/figma/webassembly-cut-figmas-load-time-by-3x/

MDN still marks WebGPU "Limited availability", not Baseline, because of the Firefox and Linux gaps. WebGPU needs HTTPS and also works in Web Workers (so rendering can move off the main thread with an OffscreenCanvas). Safari 27 beta (2026-06) adds wasm JSPI and small WebGPU features. Figma found enough driver trouble on Windows to build a live fallback from WebGPU to WebGL mid-session and a device blocklist (2025-09).

**WebAssembly features.** *Threads* need `SharedArrayBuffer`, which needs HTTPS and cross-origin isolation (`Cross-Origin-Opener-Policy` and `Cross-Origin-Embedder-Policy` headers), which blocks most third-party embeds (MDN; Godot's docs say it means "no ads, nor third-party integrations"). Godot made a single-threaded web export the default in 4.3, and Bevy's task pool "is limited to a single thread" on wasm; Bevy warns audio can stutter because "everything is single threaded". *SIMD* (fixed-width) is in all major browsers (Chrome 91, Firefox 89, Safari 16.4; secondary source). *Memory64* shipped in Chrome 133 and Firefox 134 but Safari support wasn't confirmed; SpiderMonkey's team measured it 10% to over 100% slower than 32-bit wasm and advises it only past 4 GB (2025-01-15).

**Size and startup.** Bevy's docs give a small 3D example (one model, two lights) at 13 MB of wasm by default and 4.8 MB with size optimisations and `wasm-opt`, before compression (measured July 2022; current sizes not found). Godot's docs say wasm compresses to about 25% with gzip. For JavaScript, Babylon.js 8 became "2x smaller when targeting WebGPU" by shipping WGSL shaders and dropping a 3 MB+ shader converter (2025-03-27). V8 compiles wasm while it downloads (streaming, since 2018), first with a fast baseline compiler, then optimises in the background; for very large modules full optimisation can take "30 seconds to a minute or more", which caching avoids (next section).

## 4. What others ship

- **Bevy** (Rust; 0.19, 2026-06-19): web builds work on WebGL2 by default; WebGPU on the web is "currently experimental" per its examples README. 0.19 reduced bind-group and uniform-upload overhead and made web tasks cancellable. https://bevy.org/news/bevy-0-19/
- **three.js**: WebGPURenderer with TSL (its node shader language) and automatic WebGL2 fallback; commercial blogs call it production-ready since r171 (2025), but the manual still says experimental and the many-mesh performance issue is open (section 1). https://www.utsubo.com/blog/webgpu-threejs-migration-guide (secondary)
- **Babylon.js**: WebGPU and WebGL engines; core shaders in WGSL since 8.0 (2025-03-27); snapshot rendering for WebGPU. Microsoft-backed.
- **PlayCanvas**: WebGPU path with compute and indirect draws; heavily used for Gaussian splats; WebGL2 still the main path according to an aggregator (uncertain). https://blog.playcanvas.com/tags/webgpu
- **Unity**: WebGPU backend experimental from 6.1 (2025) and **supported** from Unity 6.6 (2026-09-01), with WebGL2 still the default; unsupported on WebGPU: async compute, dynamic resolution, cubemap arrays, synchronous GPU readback. https://docs.unity3d.com/6000.6/Documentation/Manual/WebGPU.html · https://docs.unity3d.com/6000.6/Documentation/Manual/WebGPU-limitations.html · https://alternativeto.net/news/2026/9/unity-6-6-adds-webgpu-build-analysis-and-coreclr-prep/ (secondary)
- **Godot 4**: web export is WebGL2 only (Compatibility renderer); "the engine doesn't support WebGPU"; C# can't export to web. https://docs.godotengine.org/en/latest/tutorials/export/exporting_for_web.html
- **Figma**: C++ renderer compiled to wasm with Emscripten, WebGPU with live WebGL fallback, UI in the browser's own tech (2017, 2025 posts above).
- **Google Earth**: C++ compiled to wasm; in 2019 it called background threads "a clear improvement" and ran single-threaded, degraded, without them. https://web.dev/case-studies/earth-webassembly
- **High-end browser games**: no sourced example was found of a shipped browser game with visuals near modern desktop games. The strongest public demonstrations are engine samples and Unity's WebGPU feature set; that is a gap, not proof of absence.

## 5. The hybrid: JavaScript renderer, wasm simulation

The split is common. Figma keeps its engine in wasm and its interface in the browser's own tech. The usual pairing in 3D is three.js or Babylon for drawing with a wasm physics engine (Rapier, Havok, Jolt; section 7): the wasm side steps the world, and JavaScript reads positions each frame. The cost of sharing depends on how data crosses. JavaScript can view wasm memory directly as a typed array (`Float32Array::view` in Rust's `js-sys`), with **no copy**, valid only until wasm memory grows; copying out is the safe alternative. The rule from the JSON example above holds: pass one block of numbers per frame (all transforms at once), not one call per object. With threads unavailable by default, the wasm simulation runs on the main thread or in a worker that copies or transfers buffers each frame.
Sources: https://docs.rs/js-sys/latest/js_sys/struct.Float32Array.html · https://madebyevan.com/figma/webassembly-cut-figmas-load-time-by-3x/

## 6. Delivery: refresh to update

V8 caches compiled wasm when the module is loaded with `compileStreaming`/`instantiateStreaming`, is over 128 kB, comes from the **same URL**, and the server revalidates with `304 Not Modified`; a changed URL or a `200` response recompiles. It works with service workers, which can "preload new versions" so the next start is fast (V8, 2019-06-17). Figma reported in 2017 that cached wasm made load time independent of app size. So a refresh-to-update scheme works well if each release has a new file name (content hash) and old ones stay cacheable; each update costs one download and compile, and every later load is cached. These notes are for Chrome's V8; Firefox and Safari caching wasn't checked. Both clients (A and B) are delivered the same way; (A) sends one larger wasm file, (B) a JavaScript bundle plus a smaller wasm engine.
Sources: https://v8.dev/blog/wasm-code-caching · https://madebyevan.com/figma/webassembly-cut-figmas-load-time-by-3x/

**Speed in the browser.** No neutral, dated benchmark of these engines against each other in a browser was found. A 2021 developer post (2D, hardware not stated) ran Matter.js (JavaScript) beside Rapier (wasm): at 4,500 active bodies Matter held 38 FPS and Rapier 120; at 7,500, 4 against 60; Matter crashed at 9,000 while Rapier still ran 15,000 at 16 FPS. The engines differ in design as well as language, so this shows wasm's headroom rather than a clean language test. Dimforge says its fastest npm package became 2 to 5 times faster over 2025 through SIMD (2026-01-09); Babylon claimed Havok "up to 20x faster" than its older plugins (Cannon, Oimo, Ammo) (2023-04-20). Havok in Babylon already follows section 5's rule, reading results straight from wasm memory with "ideally only one wasm function call per frame" (forum, 2024-06).
Sources: https://dev.to/jerzakm/this-little-known-javascript-physics-library-blew-my-mind-57oo · https://dimforge.com/blog/2026/01/09/the-year-2025-in-dimforge/ · https://forum.babylonjs.com/t/processing-19-200-rigidbodies-with-wasm-threading/51187

**The same result on every machine.** WebAssembly helps float engines here: its core spec fixes IEEE 754 arithmetic with round-to-nearest-even and no fused multiply-add in scalar code, and lists only NaN bit patterns, relaxed SIMD, and shared-memory threads as nondeterministic. What breaks determinism is everything around the arithmetic. Rapier requires the same initial conditions, the same Rapier and compiler version, and trigonometry from its own maths library; its JavaScript guide adds the same order of adding and removing bodies, and warns that `Math.sin` and `Math.cos` are not deterministic. Jolt's cross-platform mode costs about 8% and covers different compilers (Emscripten included), systems, and processors, but its docs call it "less tested than other features". Rapier's 0.35 beta changelog (2026-08) says its deterministic mode now combines with multithreading at no measurable cost.

**Fixed point, the alternative.** Photon Quantum, a commercial deterministic netcode engine, replaces floats with its own Q48.16 fixed-point type (search excerpt). Glenn Fiedler's Fixed3D (2026-09) converts Box3D to Q48.16: bit-exact everywhere, with "uniform 1/65536 resolution across a ±1.4e14 meter world" (about 900 astronomical units), at about 2.1–2.2 times the CPU cost. Its README asks whether you should use it and answers "Probably not": Box3D "is already deterministic in floating point across platforms", and double-precision positions cost about 3%. No mature fixed-point physics crate for Rust was found.
Sources: https://github.com/WebAssembly/spec/blob/main/document/core/exec/numerics.rst · https://github.com/WebAssembly/design/blob/main/Nondeterminism.md · https://rapier.rs/docs/user_guides/rust/determinism/ · https://rapier.rs/docs/user_guides/javascript/determinism · https://raw.githubusercontent.com/jrouwe/JoltPhysics/master/Docs/Architecture.md · https://github.com/mas-bandwidth/fixed3d

**Large worlds.** A 32-bit float's step grows with distance from the origin: Godot's table gives about 0.2–0.5 mm at 2–4 km, about 4 mm at 32–65 km, and over 3 cm beyond 262 km; at Earth's radius it is about 0.38 m (developer post, 2024-04-11). The remedies are a **floating origin** (keep the player near zero and move the world) and **double precision** (Unreal Engine 5's Large World Coordinates). Jolt's double mode keeps positions accurate to thousands of kilometres for 5–10% more cost, while velocities, rotations, and the broadphase stay float; for space games its docs suggest several physics worlds (fast ships in moving ones, planets static in their own), citing X4: Foundations. Shaders stay single-precision everywhere, so drawing far from the origin needs its own trick (drawing relative to the camera), and Godot warns that origin shifting adds complexity in multiplayer.
Sources: https://docs.godotengine.org/en/stable/tutorials/physics/large_world_coordinates.html · https://frozenfractal.com/blog/2024/4/11/around-the-world-14-floating-the-origin/ · https://dev.epicgames.com/documentation/en-us/unreal-engine/large-world-coordinates-in-unreal-engine-5 · https://jrouwe.github.io/JoltPhysics/

**Orbits are not done by the physics engine.** Kerbal Space Program "simulates orbits using patched conic approximation instead of a full n-body simulation" (Wikipedia). Full rigid-body physics runs only within about 2.5 km of the active vessel; beyond that, or in time warp, a vessel goes "on rails" and only its orbit is computed (forum posts, via search excerpts). Its "Kraken" bugs came from float error far from the origin and at high speed; the fix, "Krakensbane", keeps the origin on the active vessel and absorbs its velocity into a moving frame (KSP wiki via search excerpt; Felipe Falanghe's Unite 2013 talk "Building a New Universe"). The Principia mod replaces patched conics with n-body gravity, in C++ with its own integrators. The pattern: orbits come from analytic or purpose-built integrator code, and the rigid-body engine works only in a small local bubble.
Sources: https://en.wikipedia.org/wiki/Kerbal_Space_Program · https://forum.kerbalspaceprogram.com/topic/99170-how-does-ksp-handle-out-of-range-vessels · https://wiki.kerbalspaceprogram.com/wiki/API:Krakensbane · https://forum.kerbalspaceprogram.com/topic/46361-building-a-new-universe-ksp-discussion-at-unite-2013 · https://github.com/mockingbirdnest/Principia

**How multiplayer games split authority from physics.** Rocket League is the clearest public case (Jared Cone's GDC 2018 slides, read first-hand): Psyonix put **Bullet** in place of Unreal's physics ("open-source: debuggable, modifiable", "fast single-threaded simulation") at a **fixed 120 Hz**, and the game is "100% server authoritative". The server buffers each client's inputs instead of waiting for them; the client "predicts everything", and when the server's state differs from its recorded history it reverts all physics objects to that frame and runs forward again, which at "200ms ping, 120hz = 24 correction frames". The slides rely on server correction, not bit-exact determinism, and also simplified the cars (no transmission, constant mass, simple friction curves). Photon Fusion's docs call predicting and re-simulating PhysX "multiple times per tick" expensive, and Fusion 2.1 extrapolates instead; Unity's Netcode lets each physics object be either interpolated from the server or predicted by the client.
Sources: https://media.gdcvault.com/gdc2018/presentations/Cone_Jared_It_Is_Rocket.pdf · https://doc.photonengine.com/fusion/v2/tutorials/host-mode-basics/4-physics · https://docs.unity3d.com/Packages/com.unity.netcode@1.6/manual/physics.html

## 8. Sound

**Web Audio does the mixing on its own thread.** The Web Audio spec separates the "control thread" (your script) from a "rendering thread" that runs the audio graph, in blocks of 128 frames by default (W3C draft, 2026-09-22). Chrome intends to ship a `renderSizeHint` to change the block size in Chrome 153 (blink-dev, 2026-07). An **AudioWorklet** runs custom processing, including wasm, on that audio thread (Baseline since April 2021); Chrome's design-pattern article notes the budget "is only 3ms at the sample rate of 44.1Khz" per block and describes a Worker + SharedArrayBuffer ring-buffer pattern (2018-06-18). Emscripten has built-in Wasm Audio Worklets.
Sources: https://www.w3.org/TR/webaudio-1.1/ · https://groups.google.com/a/chromium.org/g/blink-dev/c/i4c1unRSmcE · https://developer.mozilla.org/en-US/docs/Web/API/AudioWorklet · https://developer.chrome.com/blog/audio-worklet-design-pattern · https://emscripten.org/docs/api_reference/wasm_audio_worklets.html

**Spatial sound.** `PannerNode` offers `equalpower` (the default, "simple and efficient") and `HRTF`, which convolves with measured head responses (MDN). HRTF was made non-default on purpose because it "takes significant resources" (Chrome's Raymond Toy, 2014); Mozilla's Paul Adenot calls it "very expensive" and equalpower "rather cheap" (undated). No official limit on how many HRTF sources a phone can run was found. three.js's `PositionalAudio` uses HRTF for every positional sound by default (source code); Babylon's new audio engine (8.0, 2025) defaults to equalpower; PlayCanvas uses `PannerNode` with distance models.
Sources: https://developer.mozilla.org/en-US/docs/Web/API/PannerNode/panningModel · https://lists.w3.org/Archives/Public/public-audio/2014JulSep/0034.html · https://padenot.github.io/web-audio-perf/ · https://github.com/mrdoob/three.js/blob/dev/src/audio/PositionalAudio.js · https://blogs.windows.com/windowsdeveloper/2025/03/31/part-2-babylon-js-8-0-audio-gaussian-splat-and-physics-updates/ · https://github.com/BabylonJS/Babylon.js/tree/master/packages/dev/core/src/AudioV2 · https://api.playcanvas.com/engine/classes/SoundComponent.html

**Latency and quirks.** Audio can't start without a user gesture (MDN). `AudioContext` defaults to `latencyHint: "interactive"` (the lowest latency that doesn't glitch), and `baseLatency` reports what the browser actually granted (MDN). Chromium's platform buffers are 128 frames on macOS, 10 ms on Windows, 96 frames on Android (2021). One hobbyist loopback measurement found about 55–67 ms end to end at defaults, 14–19 ms tuned (2021, personal blog). iOS Safari suspends audio when the page loses focus and obeys the mute switch (WebKit bugs; details uncertain).
Sources: https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API/Best_practices · https://developer.mozilla.org/en-US/docs/Web/API/AudioContext/AudioContext · https://groups.google.com/a/chromium.org/g/blink-dev/c/dTQniJNVVMY/m/hPFwY1fbBQAJ · https://www.lesswrong.com/posts/ooXEzrX7Y9Go6D7st · https://bugs.webkit.org/show_bug.cgi?id=276016

**Libraries.** Howler.js (Web Audio with an HTML5-audio fallback and a spatial plugin) last released 2.2.4 in September 2023. In Rust, cpal (0.18.2, 2026-08-16) schedules buffers from the **main thread** by default (2,048-frame default, about 46 ms); its `audioworklet` feature runs on the audio thread but needs nightly Rust, wasm threads, and the cross-origin headers. Kira and rodio sit on cpal; Kira's README says streaming sounds don't work on wasm. Bevy's README warns of audio stutter on the web because "everything is single threaded", and its multithreading issue (open since 2022) lists AudioWorklet audio as a goal; Firewheel, planned as Bevy's next audio engine, has a worklet backend that needs nightly Rust and the headers. FMOD's HTML5 build mixes "in the game thread requiring added latency" and lacks Live Update and profiling (docs, via search excerpt). Wwise's web platform was "still behind a technical preview" in a 2023 community project quoting Audiokinetic; no general release was found.
Sources: https://github.com/goldfire/howler.js/releases · https://github.com/RustAudio/cpal · https://github.com/tesselode/kira · https://github.com/bevyengine/bevy/issues/4078 · https://github.com/BillyDM/firewheel · https://www.fmod.com/docs/2.02/api/platforms-html5.html (search excerpt) · https://github.com/msub2/wwise.js

**Does the language matter?** Only through this choice: if the client drives the browser's own node graph (sources, panners, gains), the mixing and HRTF run natively on the audio thread and Rust (through `web-sys`) or TypeScript costs the same. If a library mixes sound itself on the main thread, as the default Rust crates and FMOD's web build do, it competes with rendering and stutters when a frame runs long. Moving it into an AudioWorklet fixes that but needs threads and the headers.

## 9. Fast networking

**Transports.** WebSocket runs over TCP, so one lost packet holds up everything behind it: "The most recent data they want is delayed while waiting for old data to be resent, but by the time the resent data arrives, it's too old to be used" (Glenn Fiedler, 2017-02-26). **WebTransport** (HTTP/3 over QUIC) gives independent streams plus unreliable datagrams, which MDN suggests for "regular game state updates where each message supersedes the last one"; where QUIC is blocked it falls back to HTTP/2 over TCP with the same API (WebKit). It is now in all major browsers: Chrome 97, Firefox 114, and **Safari 26.4** (WebKit, 2026-03-24); about 91% of users per caniuse (read 2026-09-30). It needs HTTPS, works in workers, and allows short-lived self-signed certificates by hash (`serverCertificateHashes`, valid under two weeks). A secondary source reports rough edges: Safari ignores user-installed root certificates for it, and support follows the OS version (iOS and macOS 26.4). WebRTC data channels can also be unordered and unreliable (`ordered: false`, `maxRetransmits: 0`), but need signalling and STUN/TURN, which Fiedler called "dead weight" for dedicated servers; geckos.io (Node) and matchbox (Rust, peer-to-peer, for rollback) use them. Some aggregator pages still claim Firefox or Safari lack WebTransport; that is out of date.
Sources: https://gafferongames.com/post/why_cant_i_send_udp_packets_from_a_browser/ · https://developer.mozilla.org/en-US/docs/Web/API/WebTransport_API · https://webkit.org/blog/17862/webkit-features-for-safari-26-4/ · https://caniuse.com/webtransport · https://developer.mozilla.org/en-US/docs/Web/API/WebTransport/WebTransport · https://www.forasoft.com/learn/video-streaming/articles-streaming/webtransport-whip (secondary) · https://developer.mozilla.org/en-US/docs/Web/API/RTCPeerConnection/createDataChannel · https://github.com/geckosio/geckos.io · https://github.com/johanhelsing/matchbox

**Patterns.** Gabriel Gambetta's series is the standard account: the **server alone** holds the state; the client **predicts** its own moves at once and **reconciles** when the server reports the last input it processed; other entities are drawn slightly **in the past** and interpolated (about 100 ms in his example); the server **rewinds** to judge hits (lag compensation). Glenn Fiedler names three strategies for networked physics: deterministic lockstep (send only inputs; needs results "exact down to the bit-level"; one late input stalls everyone), snapshot interpolation (no determinism needed, but a buffer of about three send intervals: roughly 350 ms at 10 packets a second, 85 ms at 60), and state synchronisation (inputs plus prioritised state within a fixed budget) (2014–15). **Rollback** (GGPO, from fighting games) has every client simulate everyone, guess missing inputs, and rewind and replay when a guess was wrong; it needs a fully deterministic simulation. Tick rates in shipped games: Valorant 128, with movement and physics on "a fixed timestep: exactly 128 times per second" (Riot, 2020); Rocket League's physics 120 Hz (GDC 2018 slides, section 7); Source games 66 ticks with 100 ms interpolation by default (Valve wiki, via search excerpt); Overwatch raised updates to clients from 21 to 63 per second (press, 2016); Fortnite about 30 (press, 2018); CS2 time-stamps actions within a tick ("subtick", press, 2023).
Sources: https://www.gabrielgambetta.com/client-server-game-architecture.html · https://www.gabrielgambetta.com/client-side-prediction-server-reconciliation.html · https://www.gabrielgambetta.com/entity-interpolation.html · https://www.gabrielgambetta.com/lag-compensation.html · https://gafferongames.com/post/deterministic_lockstep/ · https://gafferongames.com/post/snapshot_interpolation/ · https://gafferongames.com/post/state_synchronization/ · https://en.wikipedia.org/wiki/GGPO · https://www.riotgames.com/en/news/peeking-valorants-netcode · https://developer.valvesoftware.com/wiki/Source_Multiplayer_Networking · https://www.ubergizmo.com/2016/09/overwatch-high-bandwidth-mode-pc · https://gamingbolt.com/epics-stunning-improvements-to-fortnite-netcode-continue-to-impress · https://gameworldobserver.com/2023/03/22/counter-strike-2-sub-tick-source-2-features-valve

**Bandwidth.** Fiedler's worked example, 901 physics cubes at 60 snapshots per second, starts at 17.4 Mbit/s and gets down to roughly 256 kbit/s by compressing rotations ("smallest three"), quantising positions (about 2 mm steps), and sending only changes against the last snapshot the client acknowledged, with still objects costing one bit (2015). Colyseus and naia likewise send only changed fields. In Rust, `postcard` and `bitcode` are compact binary formats (bitcode "uses smaller integers where possible all the way down to 1 bit"). No trustworthy per-player figures for modern commercial games were found.
Sources: https://gafferongames.com/post/snapshot_compression/ · https://github.com/jamesmunns/postcard · https://github.com/SoftbearStudios/bitcode

**Libraries (versions from crates.io, 2026-09).** *lightyear* 0.30 (Bevy): server authority, prediction with rollback, interpolation, lag compensation, and WebTransport/WebSocket for wasm; the most complete. *renet* 2.0: UDP and Steam only; its fork *renet2* 0.16 adds WebTransport and WebSocket. *naia* 0.25: server-authoritative replication over WebRTC for browsers, no built-in prediction. *bevy_replicon* 0.44: replication without its own I/O. *wtransport* 0.7 and *web-transport-quinn* 0.13 are plain WebTransport servers; wtransport says it is not yet "completely production-ready". In JavaScript, *Colyseus* is an authoritative Node framework with "delta-compressed and binary-encoded" state over WebSocket, plus an HTTP/3 transport package (0.18). The only games found using WebTransport are lightyear's own demos.
Sources: https://github.com/cBournhonesque/lightyear · https://github.com/lucaspoffo/renet · https://github.com/UkoeHB/renet2 · https://github.com/naia-lib/naia · https://github.com/projectharmonia/bevy_replicon · https://github.com/BiagioFesta/wtransport · https://github.com/colyseus/colyseus

**On AWS.** Network Load Balancers pass QUIC through and keep a client on the same server by QUIC connection ID, since 2025-11-13, so a WebTransport server can sit behind one. GameLift can generate TLS certificates for fleets. Whether GameLift supports browser WebTransport directly wasn't checked.
Sources: https://aws.amazon.com/about-aws/whats-new/2025/11/aws-network-load-balancer-quic-passthrough-mode/ · https://docs.aws.amazon.com/gamelift/latest/apireference/API_CertificateConfiguration.html

## What this means for us

- **A or B: performance really differs only on the CPU side of drawing**, in per-object bookkeeping and calls across the wasm–JavaScript boundary (sections 1–2). GPU work costs the same either way, and neither route is fast by default: both must draw many things with few calls. The JavaScript engines are mature, with WebGPU renderers still catching up; Bevy's WebGPU web build is experimental. So B (TypeScript renderer, Rust engine as wasm) is the safer start, and since the protocol is the contract, A stays open.
- **Pass one block of numbers per frame** between the engine and the renderer (all positions at once, read from wasm memory), never one call per object, as Havok does in Babylon.
- **Our whole-number engine already has what float physics engines work hardest for.** Integer arithmetic in wasm gives the same bits on every machine, with no conditions on compilers, trigonometry, or the order things were added. Float engines can now match that (Rapier, Jolt, Box3D, at 0–8% cost), but only under strict, partly tested conditions. Fixed3D shows whole numbers (Q48.16) can cover a solar system at one resolution, at about twice the CPU cost of floats.
- **Orbits belong in our laws, not a physics engine.** Every example found computes orbits with purpose-built code and uses a rigid-body engine only in a local bubble. A whole-number integrator in the engine fits, and whole numbers have the same resolution everywhere, so only drawing needs a floating origin.
- **The tension to settle: who decides a collision?** A float physics engine could give cars and ships their feel. If it decides outcomes (a crash, a hit), it has to run on the server and hand its results to the gate as whole numbers, like any law; if it runs only in the browser for looks and prediction, the server's laws stay the truth: Rocket League's shape (authority, prediction, correction). No Rust fixed-point physics engine exists, so the alternative is our own simple contact laws in whole numbers, which Rule 1 favours (Rocket League, too, simplified its cars).
- **Prediction needs the engine in the browser, but only for what the player perceives.** No oracles means the browser never holds the whole world, so it can predict the player's own vehicle and surroundings while the server corrects the rest: the thin client first, then the engine in the browser when 3D movement arrives, as `docs/ideas/web-stack.md` proposes.
- **Sound barely depends on the language.** The browser's own nodes (through three.js or Babylon; equal-power panning, HRTF only for a few near sounds) cost the same from any stack. Mixing in Rust on the web invites stutter until threads are possible.
- **Networking: WebSockets now, WebTransport for fast 3D.** WebSockets are fine for text and slow worlds. For cars and space battles, WebTransport datagrams (for state that supersedes itself) and streams (for the rest) now work in every major browser, and AWS's Network Load Balancer passes QUIC through. lightyear is the most complete Rust option but is tied to Bevy; the plain WebTransport servers are young.
- **Bandwidth matters more than the transport.** Quantised whole numbers, changes against acknowledged states, and sending only what each character perceives (which our design already requires) are how others cut traffic about seventy-fold. Shipped games update at 30 to 128 Hz (Fortnite to Valorant).
